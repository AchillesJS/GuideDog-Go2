# Восстановление запуска Gazebo — 5 ноября 2026

После сообщения «Gazebo GUI is not responding» обнаружены два оставшихся
запуска `obstacle_stop.launch.py` в ROS domain 42 / partition `guidedog_stop`.
Процессы Gazebo уже завершились, а контроллеры и наблюдатели ROS продолжали
работать. В отчётах были остановившиеся часы и отсутствие новых данных карты.
Эти два дерева процессов остановлены по конкретным PID и времени их создания.
Другие приложения не завершались.

Обычный терминал Ubuntu передавал `WAYLAND_DISPLAY=wayland-0`; в предыдущих
успешных запусках через агент использовался X11. После очистки старых сессий
и запуска с `QT_QPA_PLATFORM=xcb` сцена с роботом и коробкой снова появилась.
Это подтверждает восстановленный вариант запуска. Отдельное контролируемое
сравнение причин графического зависания не проводилось; влияние Wayland
и двух перекрывающихся сессий не разделено.

## Изменения

- `run_sim.sh` и `run_obstacle_demo.sh` по умолчанию выбирают X11/XCB для Qt.
  Настройки рабочего стола Ubuntu не меняются. Явно заданный пользователем
  `QT_QPA_PLATFORM` сохраняется.
- Supervisor удерживает файловую блокировку для пары ROS domain / Gazebo
  partition. Второй запуск через наши скрипты завершается с сообщением
  `GuideDog is already running` до создания второго дерева ROS.
- Закрытие терминала (`SIGHUP`), Ctrl+C и SIGTERM вызывают очистку принадлежащих
  запуску потомков, в том числе отсоединённых процессов Gazebo.
- Завершение включённого процесса `gazebo` инициирует завершение всего запуска
  ROS. Контроллеры и наблюдатели не остаются ждать данные после выхода Gazebo.
- `run_sim.sh` теперь использует тот же supervisor.

Защита от одновременных запусков относится к нашим скриптам. Прямой запуск
`ros2 launch` обходит supervisor и его блокировку; для обычной работы используй
скрипты проекта. Принудительное SIGKILL самому supervisor не позволяет выполнить
очистку. Существовавшие до исправления процессы были убраны отдельно.

## Проверка

67 автоматических тестов прошли, один ранее отключённый пропущен.
Новые проверки запускают настоящее дерево процессов, посылают SIGINT/SIGTERM/
SIGHUP, проверяют отказ повторного старта и сохранность постороннего процесса.
Отдельная проверка настоящего ROS Launch подтверждает остановку других дочерних
процессов после чистого выхода процесса с именем `gazebo`.

В старом тесте карты устранена зависимость от очередности доставки: кадры,
полученные до остановки потока, могут закончить ожидание TF. После опустошения
этой очереди проверяется, что продвижение часов без сканов не обновляет метку
карты. Пределы свежести данных и производственный код карты не менялись.

Ручной запуск проверен в обычном видимом терминале Ubuntu при сохранённом
Wayland-окружении и XCB для Qt. На экране подтверждена сцена, в контрольных окнах
карта продолжала принимать облака; второй запуск был отклонён. Показатели
`stale_scan` при отдельных паузах сохраняются в измерениях. Это исправление
запуска не является новым исследованием производительности симуляции.

Данные проверки: [живой запуск](validation/gui-startup-20261105/live-proof.json),
[автотесты](validation/gui-startup-20261105/pytest.xml).
Исходная диагностика и полные журналы сохранены на Mac в
`output/guidedog-gui-fix-20261105/`.

## Как запускать

```bash
~/guidedog_ws/src/GuideDog-Go2/scripts/run_local_map.sh
```

Один запуск на один канал. Для перезапуска сначала нажми Ctrl+C в его терминале
и дождись завершения. Если появляется `already running`, вернись к первому
терминалу и останови его. Повторно нажимать команду запуска для зависшего окна
не требуется. Если Gazebo не отвечает, Ctrl+C в терминале останавливает также
связанные узлы проекта.
